# LightRAG 开发任务拆解

## 1. 文档目的

本文把 `MoocHub` 的 LightRAG 接入路线拆成可执行开发任务，作为：

- 开发排期依据
- GitHub Issues 拆分依据
- 论文实现范围控制依据

原则只有一条：**不再新增新的业务功能，只做现有内容体系的 LightRAG 深化接入。**

## 2. 实施边界

### 2.1 纳入范围

- 课程
- 视频（当前作为课程内最细粒度教学单元；后续若补章节模型再细化）
- 文章
- 视频字幕/讲稿（若已具备）
- 搜索入口
- 课程详情页/文章详情页问答入口

### 2.2 暂不纳入范围

- 评论内容入知识库
- 聊天消息入知识库
- 用户画像入知识库
- 额外新业务模块

## 3. 总体拆分原则

LightRAG 路线按 6 个 issue 推进，每个 issue 都要满足：

- 有明确输入/输出
- 有落库点或接口点
- 有验收标准
- 能单独演示

## 4. Issue 拆分总览

| 编号 | 主题 | 目标 |
| --- | --- | --- |
| 1 | LightRAG 知识源整理与导出 | 把课程/章节/文章整理成标准知识文档 |
| 2 | LightRAG 索引构建与增量更新 | 建立图索引与事件驱动更新链路 |
| 3 | LightRAG 查询服务接入 | 提供 local/global/hybrid 查询接口 |
| 4 | LightRAG 问答前后端接入 | 在课程/文章场景输出带引用问答 |
| 5 | LightRAG 总结/出题/语义搜索增强 | 做教育场景能力输出 |
| 6 | LightRAG 评估、监控与论文实验 | 形成可答辩的实验与指标材料 |

## 5. 详细任务

## Issue 1：LightRAG 知识源整理与导出

### 目标

把现有课程、章节、文章内容整理成可供 LightRAG 消费的标准知识文档。

### 开发任务

- 梳理课程、章节、文章的可索引字段
- 设计统一导出结构：
  - `source_id`
  - `source_type`
  - `title`
  - `content`
  - `tags`
  - `course_id`
  - `chapter_id`
  - `source_url`
  - `updated_at`
- 增加服务端导出接口或内部导出脚本
- 若已有视频字幕/讲稿，统一并入导出格式
- 明确忽略噪声字段和隐私字段

### 验收标准

- 能导出一批标准化知识文档
- 课程、章节、文章均有稳定主键映射
- 可以单独查看任意文档的来源信息

## Issue 2：LightRAG 索引构建与增量更新

### 目标

建立 LightRAG 图结构索引，并在内容发布/修改后触发增量更新。

### 开发任务

- 部署独立 LightRAG 服务
- 设计首次离线索引构建流程
- 设计 MQ 事件：
  - `knowledge.upsert`
  - `knowledge.delete`
- 在课程/文章/章节发布与修改后发送索引更新事件
- LightRAG 服务消费事件并执行增量更新
- 增加失败重试与日志记录

### 验收标准

- 首次可完成离线建库
- 新增文章或课程内容后能触发索引更新
- 修改文章正文后能反映到后续检索结果

## Issue 3：LightRAG 查询服务接入

### 目标

为业务主系统提供稳定的 LightRAG 查询接口，而不是直接在前端调用 AI 服务。

### 开发任务

- 设计 Go -> LightRAG 服务调用协议
- 新增统一查询接口：
  - `POST /api/v1/ai/query`
- 支持查询模式：
  - `local`
  - `global`
  - `hybrid`
  - `mix`
- 支持查询范围：
  - 全局
  - 单课程
  - 单文章
- 输出结构统一为：
  - `answer`
  - `sources`
  - `entities`
  - `mode_used`
  - `confidence`
  - `trace_id`

### 验收标准

- Go 后端可稳定调用 LightRAG 查询服务
- 可以按课程或文章范围发起查询
- 返回结果包含来源引用，不是纯文本裸回答

## Issue 4：LightRAG 问答前后端接入

### 目标

在现有页面中接入 LightRAG 问答能力，形成用户可见闭环。

### 开发任务

- Flutter 课程详情页新增“智能问答”入口
- Flutter 文章详情页新增“基于本文提问”入口
- 问答结果页展示：
  - 回答正文
  - 来源引用
  - 相关课程/相关文章
  - 置信度或提示信息
- 后端增加权限与限流保护
- 记录问答请求日志与 trace

### 验收标准

- 用户可在课程页和文章页直接提问
- 回答附带来源链接或来源标题
- 弱网或失败时有明确降级提示

## Issue 5：LightRAG 总结 / 出题 / 语义搜索增强

### 目标

把 LightRAG 能力从“问答”扩展到教育场景的总结、出题和搜索增强。

### 开发任务

- 课程摘要生成
- 章节要点提炼
- 学习卡片生成
- 按章节生成题目、答案和解析
- 在现有搜索中加入语义召回与结果重排能力
- 明确哪些页面使用语义结果，哪些页面保留传统搜索结果

### 验收标准

- 可对单课程或单章节生成总结
- 可生成至少一种题型及答案解析
- 搜索结果能体现语义相关内容而非仅关键词命中

## Issue 6：LightRAG 评估、监控与论文实验

### 目标

形成可答辩、可展示、可写入论文的实验材料。

### 开发任务

- 建立测试问题集
- 建立课程/文章问答样例集
- 对比：
  - 关键词搜索
  - 传统 chunk 检索
  - LightRAG 检索
- 统计指标：
  - 命中率
  - 平均响应时延
  - 来源可解释性
  - 成本与调用量
- 增加管理侧统计看板或日志聚合
- 输出论文实验表格与案例截图

### 验收标准

- 有一套固定样例问题集
- 有可展示的对比结果
- 有可直接进入论文的指标表和示例图

## 6. 实施顺序建议

按依赖关系，建议严格按下列顺序执行：

1. `Issue 1` 知识源整理与导出
2. `Issue 2` 索引构建与增量更新
3. `Issue 3` 查询服务接入
4. `Issue 4` 问答前后端接入
5. `Issue 5` 总结/出题/语义搜索增强
6. `Issue 6` 评估、监控与论文实验

原因很直接：

- 没有标准知识源，就没有稳定索引
- 没有索引更新链路，问答结果就不可维护
- 没有查询接口，前端就无法稳定接入
- 没有评估，就无法证明 LightRAG 路线优于普通检索

## 7. 每个 Issue 的完成定义

每个 issue 完成时，至少要同时满足：

- 代码已合并到主干
- README / 文档已更新
- 有可复现演示步骤
- 有最小测试或验收记录
