# MoocHub 接入 LightRAG 路线说明

## 1. 文档目的

本文用于明确 `MoocHub` 后续的 AI 深化路线：**不再继续扩展新的业务功能**，而是在现有课程、文章、视频、搜索、推荐、后台发布体系基础上，接入 **LightRAG** 作为论文与系统亮点。

这里的 `LightRAG` 指的是论文 **LightRAG: Simple and Fast Retrieval-Augmented Generation** 中提出的技术路线，而不是泛化意义上的“传统 RAG”。

## 2. 先说结论：本项目接入的不是传统 RAG

### 2.1 传统 RAG 的典型做法

传统 RAG 往往是以下流程：

1. 把文档切成 chunks
2. 做 embedding
3. 用户提问时做向量召回
4. 把召回片段拼进 prompt，让大模型回答

这条路线实现简单，但问题也明显：

- 文档之间的实体关系弱，难以表达“课程 - 章节 - 知识点 - 文章 - 术语”之间的关联
- 对跨段、跨文档问题支持一般
- 新增内容后往往只是“再插入几个 chunk”，上下文结构感不强
- 很容易退化成“相似段落搜索 + 大模型复述”

### 2.2 LightRAG 的核心差异

根据论文与官方实现，LightRAG 的关键点不是“只做向量检索”，而是：

- **把图结构引入索引阶段**：不仅存 chunks，还抽取实体与关系，构建知识图
- **双层检索（dual-level retrieval）**：
  - 低层：面向局部、细粒度、上下文相关信息
  - 高层：面向全局、主题级、跨文档知识发现
- **图 + 向量联合检索**：不是只查 embedding，也会利用实体和关系
- **支持增量更新**：新内容进入后，不是简单“追加若干 chunk”，而是持续更新图谱与检索结构

因此，MoocHub 的 LightRAG 路线应理解为：

> 以课程与文章知识为中心，构建“文本块 + 实体关系图 + 多模式查询”的检索增强体系。

这才是论文路线，不是普通知识库问答壳子。

## 3. LightRAG 为什么适合 MoocHub

MoocHub 当前已经具备较完整的数据与业务底座：

- 课程、章节、视频、文章、分类、搜索
- 教师/管理员发布内容
- 评论、收藏、学习进度、埋点与推荐
- MinIO 对象存储、Redis 缓存、RabbitMQ 异步事件

这些能力说明项目已经不是“从零做一个 AI Demo”，而是一个有稳定内容生产链路的学习平台。LightRAG 接入的价值就在于：

1. **把已有内容变成结构化知识**
   - 课程简介、章节标题、文章正文、术语说明、视频讲解文本可以被统一组织
2. **把搜索升级为知识检索**
   - 不再只是标题匹配或关键词过滤，而是支持概念关联与主题级查询
3. **把问答变成课程型问答**
   - 用户问“Spring Boot 依赖注入和 IOC 是什么关系”，系统不仅找相似段落，还能串出课程章节与相关文章的关联
4. **把论文亮点落到工程里**
   - 论文可明确论证：MoocHub 并非接一个通用聊天 API，而是基于 LightRAG 论文路线做了教育知识增强系统

## 4. MoocHub 的接入目标

本项目接入 LightRAG 后，目标不是“大而全 AI 平台”，而是聚焦 4 类教育场景：

### 4.1 课程/文章问答

- 基于课程、章节、文章知识回答问题
- 回答中返回引用来源
- 明确答案来自哪篇文章、哪门课程、哪一章节

### 4.2 内容总结

- 课程摘要
- 章节知识点提炼
- 文章要点总结
- 学习卡片生成

### 4.3 自动出题

- 基于课程章节生成选择题、判断题、简答题
- 给出答案与解析
- 支持按章节或知识点出题

### 4.4 语义搜索增强

- 不再局限于关键词搜索
- 支持“概念相近”“关系相邻”“主题相关”的检索
- 与现有搜索结果混排或重排结合

## 5. 数据接入边界

为了保证论文路线可控，LightRAG 第一阶段**只接入高质量教学内容**，不把所有业务数据一股脑塞进去。

> 当前代码模型中暂无独立 `chapter` 表，因此第一版以 `course / video / article` 为实际知识源粒度；如果后续补充章节模型，再把 `video` 下沉为更细粒度章节单元。

### 5.1 第一批纳入 LightRAG 的数据

- 课程标题、课程简介、课程分类
- 章节标题、章节简介
- 文章标题、文章摘要、文章正文、文章标签
- 视频标题、视频简介
- 视频字幕/讲稿/转写文本（如果已有）

### 5.2 暂不纳入的内容

- 评论区内容
- 私聊/群聊消息
- 用户个人资料
- 行为埋点原始明细

原因很简单：

- 评论和聊天噪声大，容易污染实体抽取和关系图
- 用户隐私数据不应进入公共知识检索层
- 埋点数据适合做推荐和分析，不适合直接做教学知识问答

## 6. 目标架构：Go 主系统 + 独立 LightRAG 服务

### 6.1 不建议把 LightRAG 直接硬塞进现有 Go 进程

原因：

- LightRAG 官方核心实现与服务侧生态是 Python 路线
- 图谱抽取、embedding、LLM 调用链更适合独立 AI 服务维护
- 这样不会破坏现有 Go 后端稳定性

### 6.2 推荐架构

建议采用以下分层：

1. **业务主系统（现有 Go 服务）**
   - 负责课程、文章、章节、用户、权限、发布审核
   - 负责对外统一 API

2. **LightRAG 服务（新增 Python 服务）**
   - 负责文档入库
   - 负责实体/关系抽取
   - 负责图谱与检索索引维护
   - 负责查询与回答生成

3. **对象与数据来源**
   - MySQL / MongoDB：业务主数据
   - MinIO：文章图片、视频资源、字幕文件
   - RabbitMQ：发布/更新事件驱动增量索引

### 6.3 推荐调用链

- 教师/管理员发布课程、文章、章节后
- Go 服务写库成功
- 同步或异步发出“知识索引更新事件”
- LightRAG 服务消费事件，执行增量更新
- 用户在 App 侧提问或搜索时
- Go 服务调用 LightRAG 服务查询结果
- Go 服务统一封装后返回给 Flutter

当前项目的骨架实现是：

- Go 服务发布 `knowledge.sync` 事件
- 若配置了 `LIGHTRAG_SYNC_URL`，则后端 worker 会把事件转发给外部 LightRAG 服务
- 若未配置 `LIGHTRAG_SYNC_URL`，worker 不启动，主业务链路不受影响

## 7. 按论文路线设计索引，不按普通 chunk 方案设计

### 7.1 LightRAG 索引对象

MoocHub 的知识索引至少包含三层对象：

1. **文档层**
   - 课程文档
   - 文章文档
   - 章节文档
   - 字幕文档

2. **文本块层**
   - 文档切片后的 chunk
   - 与来源课程、文章、章节建立映射

3. **实体关系层**
   - 例如：`Spring Boot`、`依赖注入`、`IOC`、`事务传播`、`MySQL 索引`
   - 以及实体之间的关系：
     - 包含
     - 依赖
     - 对比
     - 实现
     - 适用场景
     - 前置知识

### 7.2 MoocHub 适合抽取的实体类型

建议第一版限定实体类型，避免图谱发散：

- 课程
- 章节
- 技术概念
- 框架/库
- 编程语言
- 数据库/中间件
- 算法/模型
- 关键术语

### 7.3 MoocHub 适合抽取的关系类型

建议第一版限定关系类型：

- 属于
- 包含
- 依赖于
- 对比于
- 实现于
- 用于
- 前置知识
- 延伸阅读

这一步非常关键。论文里强调的是 **graph-based indexing**，所以系统不能只保留 chunk 向量，而要把课程内容组织成“可检索的知识关系结构”。

## 8. 检索路线：必须体现 LightRAG 的双层检索

### 8.1 查询类型划分

MoocHub 的用户问题大致可以分成三类：

1. **局部问题**
   - “Spring IOC 是什么？”
   - “事务传播有哪几种？”

2. **全局问题**
   - “Java 后端开发的学习路径怎么安排？”
   - “数据库课程和缓存课程之间的知识关系是什么？”

3. **混合问题**
   - “为什么 Spring Boot 课程里讲依赖注入时要先理解 IOC 和 Bean 生命周期？”

### 8.2 对应 LightRAG 查询模式

根据官方实现，LightRAG 支持多种 query mode，包括：

- `local`
- `global`
- `hybrid`
- `naive`
- `mix`

MoocHub 的推荐映射如下：

- **局部问答** -> `local`
  - 查局部上下文、相关 chunk、近邻实体
- **综述/路径类问题** -> `global`
  - 查全局主题、跨文档关联
- **课程型复杂问题** -> `hybrid` 或 `mix`
  - 联合局部细节与全局结构

这部分要在论文里明确写出：**系统不是统一走一个“向量召回模式”**，而是根据问题类型选择 LightRAG 的查询模式。

## 9. 增量更新路线

论文明确强调 LightRAG 支持 **incremental update**。这对 MoocHub 很关键，因为平台内容是持续发布的。

### 9.1 需要触发增量更新的事件

- 新建课程
- 修改课程简介
- 新增章节
- 修改章节标题/简介
- 发布文章
- 更新文章正文
- 上传视频字幕或课程讲稿

### 9.2 增量更新机制建议

1. Go 服务在内容变更后发 RabbitMQ 事件
2. 事件内容包括：
   - 资源类型（course/article/chapter/video_transcript）
   - 资源 ID
   - 操作类型（create/update/delete）
   - 更新时间
3. LightRAG 服务消费事件后：
   - 拉取最新内容
   - 重建对应文档的 chunk
   - 重抽实体与关系
   - 更新局部图谱与检索索引

### 9.3 不建议第一版做的事

- 不建议全量重建整个知识库
- 不建议每次内容修改都全量重跑 embedding + graph rebuild

否则工程成本高，也无法体现 LightRAG 的论文优势。

## 10. MoocHub 的具体落地阶段

## 阶段 A：知识源准备

目标：先把“可用知识”整理出来。

工作项：

- 梳理课程、章节、文章字段
- 增加课程字幕/讲稿导入能力（如没有字幕，可先人工准备少量示例文本）
- 统一导出给 LightRAG 的文档格式
- 生成 `source_id / source_type / source_title / source_url`

交付物：

- 一套可被 LightRAG 消费的标准知识文档流

## 阶段 B：离线索引构建

目标：完成第一版知识图索引。

工作项：

- 文章与课程简介先入库
- 课程章节文本纳入
- 构建 chunk + entity + relation + source 映射
- 试运行 `local/global/hybrid` 查询

交付物：

- 第一版教学知识图
- 第一版问答接口

## 阶段 C：在线增量更新

目标：把发布流程接进知识更新链路。

工作项：

- 发布后发 MQ 事件
- LightRAG 服务增量更新索引
- 更新失败记录日志与重试

交付物：

- 内容发布 -> 知识索引更新闭环

## 阶段 D：用户能力输出

目标：把 AI 能力真正接到产品上。

工作项：

- 课程问答入口
- 文章问答入口
- 章节摘要生成
- 自动出题与解析
- 搜索重排增强

交付物：

- 可演示的 LightRAG 教学助手能力

## 11. API 设计建议

### 11.1 索引侧接口

- `POST /api/v1/ai/knowledge/rebuild`
  - 全量重建（仅管理员）
- `POST /api/v1/ai/knowledge/upsert`
  - 单资源增量更新
- `POST /api/v1/ai/knowledge/delete`
  - 删除资源知识索引

### 11.2 查询侧接口

- `POST /api/v1/ai/query`
  - 入参：
    - `query`
    - `mode` (`local/global/hybrid/mix`)
    - `scope` (`course/article/all`)
    - `course_id`（可选）
    - `article_id`（可选）
  - 出参：
    - `answer`
    - `sources`
    - `entities`
    - `mode_used`
    - `confidence`
    - `trace_id`

### 11.3 生成侧接口

- `POST /api/v1/ai/summary/course`
- `POST /api/v1/ai/summary/chapter`
- `POST /api/v1/ai/quiz/generate`

## 12. 客户端接入建议

Flutter 端不需要引入复杂 AI SDK，只要新增几个明确入口：

- 课程详情页：`AI 问答`
- 章节页：`本章总结`
- 学习页：`智能出题`
- 搜索页：`语义搜索`

展示层要注意：

- 回答必须展示引用来源
- 要标出答案来自哪门课程/哪篇文章
- 要区分“AI 生成内容”和“原始教学内容”

否则系统看起来就像普通聊天机器人，不像教育知识助手。

## 13. 论文亮点应如何表述

如果后续写论文，建议把亮点表述为下面这类内容：

### 13.1 不是“接入大模型”，而是“接入 LightRAG 论文路线”

论文重点不应写成：

- 接入某个 LLM
- 做了一个问答功能

而应写成：

- 基于 LightRAG 的图结构索引与双层检索机制
- 面向在线教育内容的知识增强问答系统
- 支持课程/文章/章节多源知识统一组织
- 支持发布驱动的增量更新

### 13.2 论文可验证点

- 与普通关键词搜索对比
- 与传统 chunk-only RAG 对比
- `local/global/hybrid` 不同模式下的效果对比
- 增量更新前后索引时延对比
- 问答准确性、来源可解释性、响应延迟对比

## 14. 风险与约束

### 14.1 实体抽取质量依赖模型能力

如果使用较弱模型做实体关系抽取，可能会出现：

- 实体抽不准
- 关系过少
- 图谱断裂

因此第一版要控制语料范围，不要一开始就全量上所有课程。

### 14.2 视频内容如果没有字幕，知识覆盖会不完整

LightRAG 依赖可索引文本。没有字幕的视频只靠标题和简介，知识密度不够。

所以建议：

- 第一版优先文章 + 课程简介 + 章节文本
- 第二版补视频字幕/讲稿

### 14.3 评论内容不适合直接混入知识图

评论噪声高，会污染图谱与问答结果。评论更适合做舆情、热度和推荐，不适合作为教学知识主语料。

## 15. 建议的最小可交付版本

如果时间有限，建议只做一个**论文可答辩的最小闭环**：

1. 接入文章正文 + 课程简介 + 章节文本
2. 用独立 Python LightRAG 服务完成索引
3. Go 服务对接查询接口
4. Flutter 增加一个课程问答入口
5. 回答中返回来源引用
6. 支持发布后增量更新

这个闭环已经足够支撑论文亮点，因为它已经体现了：

- LightRAG 图结构索引
- 多模式检索
- 增量更新
- 教育场景落地

## 16. 本项目的执行建议

当前阶段建议把后续工作收敛为以下顺序：

1. 先整理知识源字段与导出格式
2. 再独立部署 LightRAG 服务
3. 先做离线索引，再做增量更新
4. 先做课程/文章问答，再扩展总结与出题
5. 最后补评估、成本和论文实验

这是风险最低、最符合当前毕业设计阶段的路线。
